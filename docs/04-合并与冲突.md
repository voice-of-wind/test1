# 04 · 合并与冲突：Git 里最需要练的一节

> 冲突不是错误，是 Git 在说："这里两边都改了，我不替你决定，你来。"
> 解决冲突的能力，是 Git 熟练度和新手的分水岭。

---

## 1. `git merge` 的三种结果

假设你在 `main` 上执行：

```powershell
git merge feature/search
```

### 结果一：Already up to date

`feature/search` 的所有提交，`main` 早就有了，什么都不用做。

```text
Already up to date.
```

### 结果二：快进合并（Fast-forward）

`feature/search` 是从 `main` 当前这个位置直接往前长的，中间没有分叉：

```text
合并前：
  A ← B ← C          ← main（HEAD）
           ↑
       feature

合并后：
  A ← B ← C          ← main, feature（都指向 C）
```

Git 只需要把 `main` 这个指针往前挪一格：

```text
Updating 22230a1..042f020
Fast-forward
 README.md           | 1 +
 tests/test_store.py | 6 ++++++
 todo/cli.py         | 13 +++++++++++++
 todo/store.py       | 9 +++++++++
 4 files changed, 29 insertions(+)
```

**没有产生新的提交。** 历史是一条直线。

### 结果三：三方合并（3-way merge，产生 merge commit）

两条分支各自往前走了，分叉了：

```text
合并前：
        D ← E        ← main（HEAD）
       /
  A ← B
       \
        F ← G        ← feature

合并后：
        D ← E ←──── M    ← main（HEAD）
       /          /
  A ← B         /
       \       /
        F ← G
```

Git 需要比较三个东西：**E（你这边的末端）、G（那边的末端）、B（共同祖先）**，这就是"三方"的由来。

```text
Merge made by the 'ort' strategy.
 README.md           | 1 +
 tests/test_store.py | 6 ++++++
 todo/cli.py         | 13 +++++++++++++
 todo/store.py       | 9 +++++++++
 4 files changed, 29 insertions(+)
```

产生了一个新的提交 `M`，它有**两个父提交**。这就是"合并提交"。

### `--no-ff`：强制留下合并痕迹

```powershell
git merge --no-ff feature/search -m "merge: 合并搜索功能"
```

即使能快进，也强行造一个 merge commit。好处是历史里保留了"这里有一整条功能分支"的信息，`git log --graph` 上一眼能看出功能边界。很多团队对主干就用 `--no-ff`。

| 方式 | 历史形态 | 适合 |
| --- | --- | --- |
| 默认（能快进就快进） | 直线，看不出分支 | 个人项目、小改动 |
| `--no-ff` | 有闭环的合并线 | 团队主干，保留功能边界 |
| `--squash` | 压成一个普通提交，**不产生合并关系** | 分支上提交很碎，只想留一条 |

> `--squash` 的坑：它不会把两个分支"连起来"，Git 不认为那些提交被合并了。之后再想合并同一个分支，还得再处理一次。新手期先用默认和 `--no-ff`。

## 2. 冲突是怎么产生的

**同一个文件的同一段区域，被两边改成了不同的样子。**

Git 的自动合并很聪明：改动在不同位置、不同文件，它都能自动拼好（这就是为什么 lab04 里 4 个文件冲突，但如果只改不同函数就不会冲突）。

它算不出来的是这种：

```text
base:     | rm | 删除任务 |
你的分支:  | rm | 删除任务 |
           | search | 按关键词搜索 |        ← 你在同一行后面插了一行
对方分支:  | rm | 删除任务 |
           | stats | 看统计 |              ← 他也在同一行后面插了一行
```

两边都基于"那一行"，但都改了它周围的内容，Git 无法判断谁先谁后、要不要都留，于是停下来问你。

### 冲突时的现场

```powershell
git merge feature/stats
```

```text
Auto-merging README.md
CONFLICT (content): Merge conflict in README.md
Auto-merging tests/test_store.py
CONFLICT (content): Merge conflict in tests/test_store.py
Auto-merging todo/cli.py
CONFLICT (content): Merge conflict in todo/cli.py
Auto-merging todo/store.py
CONFLICT (content): Merge conflict in todo/store.py
Automatic merge failed; fix conflicts and then commit the result.
```

`git status` 变成：

```text
On branch main
You have unmerged paths.
  (fix conflicts and run "git commit")
  (use "git merge --abort" to abort the merge)

Unmerged paths:
  (use "git add <file>..." to mark resolution)
        both modified:   README.md
        both modified:   tests/test_store.py
        both modified:   todo/cli.py
        both modified:   todo/store.py

no changes added to commit (use "git add" and/or "git commit -a")
```

**注意：合并没有完成。** 仓库现在处于"合并中"状态，`git commit` 会提交这次合并，`git merge --abort` 会退回去。

## 3. 冲突标记怎么读

打开冲突文件，会看到这种结构：

```python
    p_list = sub.add_parser("list", help="列出未完成任务")
    p_list.add_argument("-a", "--all", action="store_true", help="连已完成的一起列")

<<<<<<< HEAD
    p_search = sub.add_parser("search", help="按关键词搜索任务")
    p_search.add_argument("keyword", help="要搜的词")
=======
    p_stats = sub.add_parser("stats", help="看统计")
    p_stats.add_argument("--json", action="store_true", help="用 JSON 输出")
>>>>>>> feature/stats

    p_done = sub.add_parser("done", help="把任务标记为完成")
```

| 标记 | 意思 |
| --- | --- |
| `<<<<<<< HEAD` | 从这里开始是**你当前所在分支**（你执行 merge 时站的那条）的内容 |
| `=======` | 分隔线 |
| `>>>>>>> feature/stats` | 到这里结束，是**被合并进来的分支**的内容 |

**"HEAD 这边 = 我的，另一边 = 他的"** ——在 `merge` 时成立。

> ⚠️ **在 `rebase` 时不成立，而且是反的！** rebase 时 HEAD 是"别人的基底"，`--theirs` 反而是你自己的改动。这是 Git 最坑的命名之一，docs/06 会再强调。

### 冲突只可能出现在这三行之间

`<<<<<<<`、`=======`、`>>>>>>>` 之外的代码都是 Git 已经合好的，**不要动**。你只需要处理标记之间的部分：

1. 两段都留（最常见）
2. 只留一段
3. 改写成一个新的版本（两边都不完全要）

然后**把三行标记删掉**。标记是给人看的，不能留在代码里。

## 4. 解决冲突的标准流程

```powershell
# ① 先看全局：哪些文件冲突了
git status

# ② 逐个文件打开，处理标记，删掉 <<<<<<< ======= >>>>>>>

# ③ 检查有没有漏网的标记（保险）
git diff --check

# ④ 标记为已解决
git add README.md todo/cli.py todo/store.py tests/test_store.py
# （git add 就是"我解决好了"的信号）

# ⑤ 确认所有冲突都标记完了
git status          # 应该从 "Unmerged paths" 变成 "All conflicts fixed"

# ⑥ 提交这次合并
git commit -m "merge: 合并统计功能"
```

第 ⑥ 步如果用 `git commit` 不带 `-m`，Git 会打开编辑器，里面已经预填好了 `Merge branch 'feature/stats' into main`，你可以直接用或补充说明。

### 关键：解决完必须验证

```powershell
python -m unittest discover -s tests -v
```

**测试全绿才算解决完。** 这一步是很多人跳过的，也是"冲突解完了但功能坏了"的根源：

> 冲突标记删干净了、代码能跑了，但你把对方的一个函数删掉了 —— **语法正确，语义错误**。
> 只有测试（或手动跑一遍）能发现。

lab04 里的 4 文件冲突，就是按这个标准验收的。

### 想放弃？`git merge --abort`

```powershell
git merge --abort
```

回到合并前一模一样的状态，工作区也恢复。**在自己搞不清状况时，这是最安全的一步**，比硬着头皮解完强。

（注意：`--abort` 会丢掉你在合并过程中改的东西。如果解到一半想留着，先 `git stash push -m "解冲突到一半"`。）

## 5. 三个高频坑

### 坑 1：`--ours` / `--theirs` 记反

```powershell
git checkout --ours  todo/cli.py    # 整个文件用"我这边"的版本
git checkout --theirs todo/cli.py   # 整个文件用"他那边"的版本
```

- 在 **merge** 时：`ours` = 你当前分支，`theirs` = 被合进来的分支。符合直觉。
- 在 **rebase** 时：**反过来**。`ours` = 你 rebase 到的那条基线（别人的），`theirs` = 你自己正在重放的提交。

**记不住就别用。** 整个文件选一边，通常会丢掉另一边的功能。老老实实手工改，或者用编辑器的三方合并界面。

### 坑 2：以为 `git add` 之后冲突就解决了

`git add` 只是**声明**"我处理好了"。它不检查你处理得对不对，甚至不检查标记删没删干净。Git 完全信任你。

所以：`git add` 之前先自己扫一眼标记。

### 坑 3：解决冲突时顺手改了别的东西

冲突文件里同时有"冲突区域"和"已经合好的区域"。你为了解决冲突去改已经合好的部分，就把对方的工作改了。

**只动标记之间的部分**，其他一律不碰。

## 6. 用工具解决（比手工快很多）

### VS Code

打开冲突文件，VS Code 会显示：

```text
Accept Current Change | Accept Incoming Change | Accept Both Changes | Compare Changes
```

- **Accept Both Changes** 是大部分冲突的正确起点（然后手工调整顺序/去重）
- **Compare Changes** 打开三栏视图（左边你的、右边他的、中间结果），大文件冲突必用

命令行调起合并工具：

```powershell
git mergetool            # 会找你配置过的工具
git config --global merge.tool vscode
git config --global mergetool.vscode.cmd 'code --wait --merge $REMOTE $LOCAL $BASE $MERGED'
```

### 实在乱了：`git checkout --conflict=diff3`

```powershell
git checkout --conflict=diff3 todo/store.py
```

会在冲突里额外显示**共同祖先**的版本：

```python
<<<<<<< HEAD
    你的版本
||||||| merged common ancestors
    原来的版本          ← 多出来的这段，能帮你想清楚"我们各自改了什么"
=======
    对方的版本
>>>>>>> feature/stats
```

看到"原来的样子"，往往立刻就知道该怎么合。

## 7. 怎么少踩冲突

冲突的根源不是 Git，是**两条分支在同一片代码上并行改太久**。

| 做法 | 效果 |
| --- | --- |
| 分支活不过 2 天 | 冲突窗口小 |
| 每天开工先 `git pull` / `git rebase main` | 早点面对冲突，早解决 |
| 一个分支只做一件事 | 冲突范围小、review 也容易 |
| 提交小、频繁 | 冲突粒度细，好解 |
| 模块边界清楚（不同文件/不同类） | 物理上就不冲突 |
| 别顺手格式化整个文件 | 假冲突的最大来源 |

反过来说：**冲突多，通常是协作方式的问题，不是 Git 的问题。**

---

## 8. 记住这四条

1. 冲突 = 两边改了同一处，Git 让你决定。
2. **只处理 `<<<<<<<` 到 `>>>>>>>` 之间**，删干净标记。
3. 解完必须**跑测试**——语法对不等于语义对。
4. 乱了就 `git merge --abort`，重来一遍不丢人。
