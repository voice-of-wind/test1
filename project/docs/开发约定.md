# 开发约定

这份文件是"团队规矩"的样子。练习的时候按它来，习惯就带出去了。

## 提交信息

格式：

```text
<类型>(<范围>): <一句话说明>

<可选正文：为什么这么改>
```

类型只用这几个：

| 类型 | 用在哪 |
| --- | --- |
| `feat` | 新功能 |
| `fix` | 修 bug |
| `docs` | 只改文档 |
| `test` | 只改测试 |
| `refactor` | 不改行为的重构 |
| `chore` | 杂活：依赖、配置、脚本 |

例子：

```text
feat(cli): 支持用 -t 给任务打多个标签
fix(store): 修复空文件导致启动崩溃
docs(readme): 补充 Windows 下的引号注意事项
```

好的提交信息回答两个问题：**改了什么**、**为什么**。不好的例子：`update`、`修改`、`fix bug`、`111`。

## 分支命名

```text
feature/search        新功能
fix/empty-json        修 bug
docs/git-guide        文档
chore/bump-python     杂活
```

规则：小写、用连字符、带上类型前缀。不要 `test`、`dev1`、`我的分支` 这种名字。

## 一次提交的粒度

一句话能说清、能单独回滚的一件事，就是一次提交。

不要把"加功能 + 顺手改了十个文件格式 + 删了注释"塞进同一个 commit。

## 合入前检查

- [ ] `python -m unittest discover -s tests -v` 全绿
- [ ] `git status` 里没有意料之外的文件（尤其是 `data/tasks.json`、`__pycache__`）
- [ ] 提交信息符合上面的格式
- [ ] 分支是从最新的 `main` 拉出来的
