# 07 · 团队日常：规范与配置

> 这一章讲的是"在真实项目里，怎么不给人添麻烦"。
> 技术只占一半，另一半是约定。

---

## 1. 一天的工作流

```text
09:30   git switch main && git pull          拉最新
09:32   git switch -c feature/search         开分支
09:35   ...写代码...
10:20   git add -p && git commit            提交一个小步
10:25   ...写代码...
11:00   git commit
11:10   跑测试 → 全绿
11:15   git push -u origin feature/search   推上去
11:20   开 PR，@同事 review

（收到意见）
14:00   改代码 → commit → git push           PR 自动更新
15:00   review 通过 → 网页上 squash merge
15:05   git switch main && git pull
15:06   git branch -d feature/search        清理
```

**关键点：**

- 每天开工先 `pull`，别攒一周再合
- 提交频率按"一件事"算，不按"一天"算
- push 之前跑测试（CI 会拦，但别浪费 CI 时间）
- 合并完立刻清理本地分支，不然半年后一百条分支

## 2. 分支策略：选简单的那种

### 推荐：主干开发 + 短分支（trunk-based）

```text
main ──●──●──────●──────●──→     永远可发布
        \        /
         ●──●──●                功能分支，活不过 2 天
```

- 只有 `main` 是长期分支
- 功能分支从 main 拉，合回 main，删掉
- 靠 CI + review 保证 main 的质量
- 需要发布时打 tag

**适合大多数团队。** 分支少、冲突少、心智负担小。

### GitFlow（重，多数团队不需要）

```text
main       ─────────●─────────●──→   只放已发布版本
            \      /  \       /
release      ●────●    ●─────●       发布分支
            /              /
develop ──●──●──●──●──●──●──→        集成分支
           \    /
feature     ●──●
```

`main` / `develop` / `release/*` / `feature/*` / `hotfix/*` 五套分支。适合"有明确版本发布周期、需要同时维护多个已发布版本"的软件（比如客户端）。**Web 服务用它基本是自找麻烦。**

先学简单的那套，遇到真需要再升级。

## 3. 提交信息规范

### 为什么值得规范

- `git log --oneline` 扫一眼就知道每个版本干了什么
- 能自动生成 changelog
- 出问题时 `git log --grep="fix:"` 能快速找到修过什么
- 半年后的你（和接手的同事）会感谢现在的你

### 约定式提交（Conventional Commits）

```text
<类型>(<范围>): <说明>

<正文，可选>

<脚注，可选>
```

类型：

| 类型 | 含义 | 出现在 changelog 吗 |
| --- | --- | --- |
| `feat` | 新功能 | ✅ |
| `fix` | 修 bug | ✅ |
| `docs` | 只改文档 | ❌ |
| `test` | 只改测试 | ❌ |
| `refactor` | 重构，不改行为 | ❌ |
| `perf` | 性能优化 | ✅ |
| `chore` | 杂活：依赖、配置、脚本 | ❌ |
| `build` / `ci` | 构建、流水线 | ❌ |

例子：

```text
feat(store): 支持按关键词搜索
fix(cli): 修复空 JSON 文件导致启动崩溃
refactor(models): 把格式化逻辑从 CLI 挪进 Task
docs(readme): 补充 Windows 下的引号注意事项
```

### 三条实用规则

1. **标题行不超过 50 个字符**，句尾不加句号，用祈使语气（"支持搜索"而不是"支持了搜索"）
2. **标题说"做了什么"，正文说"为什么"**
3. **一次提交只做一件事**——这条比格式重要十倍

### 反例

```text
update            ← 更新了什么？
fix bug           ← 哪个 bug？
111               ← ？
修改               ← 改了啥？
feat: 大改         ← 大改是多大？
```

## 4. `.gitignore`：什么不该进仓库

```gitignore
# 注释用 #
__pycache__/          # 目录
*.py[cod]             # 通配符
.venv/
data/                 # 整个目录
!data/sample.json     # ! 开头 = 例外，仍然要跟踪
config/local.*.json
```

规则：

- `/xxx` 只匹配仓库根目录；`xxx/` 匹配任意层级的同名目录
- `*` 不跨 `/`；`**` 跨层级
- **子目录里的 `.gitignore` 只影响那个子目录**
- 优先级：后写的覆盖先写的

### 最大的坑：已经跟踪的文件，加进 `.gitignore` 也没用

```powershell
git status            # data/tasks.json 是 ?? （未跟踪）→ 加 ignore 立刻生效
```

但如果它**已经提交过**：

```powershell
git rm --cached data/tasks.json     # 从版本控制移除，但保留本地文件 ★
git commit -m "chore: 不再跟踪本地数据"
```

注意 `--cached`：不加会把本地文件也删掉。

### 该 ignore 什么

| 该 ignore | 不该 ignore |
| --- | --- |
| 编译产物（`__pycache__/`、`dist/`） | 源码 |
| 依赖目录（`.venv/`、`node_modules/`） | 依赖清单（`requirements.txt`、`package-lock.json`）★ |
| 本地配置（含密钥、路径） | 配置模板（`.env.example`） |
| 日志、临时文件 | 数据库迁移脚本 |
| 编辑器私有配置（`.vscode/`） | 团队共享的编辑器配置（`.editorconfig`） |

**`package-lock.json` / `poetry.lock` 这类锁文件一定要提交**——它保证所有人装到一样的版本。

## 5. 换行符：Windows 上最烦人的问题

### 问题是什么

Windows 用 `CRLF`（`\r\n`），Mac/Linux 用 `LF`（`\n`）。如果不管，跨平台协作时每个文件都会显示"整行都改了"，diff 全是噪声。

### 怎么解决：`.gitattributes`

项目里的 `project/.gitattributes` 已经配好了：

```gitattributes
# 仓库里、工作区里都统一用 LF
* text=auto eol=lf

# 二进制文件必须声明，否则 git 会尝试转换，把文件弄坏
*.png binary
*.jpg binary
*.ico binary
*.zip binary
```

两行合起来的含义：

- `text=auto`：让 git 自己判断哪些文件是文本（看内容里有没有二进制字节），是文本就按换行符规则处理
- `eol=lf`：**检出时也用 LF**，不要转成 CRLF

**为什么一定要写 `eol=lf`？** 只写 `text=auto` 时，Windows 上检出会按 `core.eol`（默认 `native`）转成 CRLF，于是你每次 `git add` 都会看到：

```text
warning: in the working copy of 'todo/store.py', LF will be replaced by CRLF the next time Git touches it
```

加上 `eol=lf` 之后就没有这个警告了，而且 Windows / Mac / Linux 三边行为完全一致——**这是我实测过的结论，也是本项目为什么这么配的原因。**

配合（README 里已经配过）：

```powershell
git config --global core.autocrlf false
```

### 三种 `core.autocrlf` 配置

| 值 | 行为 | 适合 |
| --- | --- | --- |
| `true` | 提交时 CRLF→LF，检出时 LF→CRLF | 纯 Windows 团队、老项目 |
| `input` | 提交时 CRLF→LF，检出时**不转换** | Windows 上写跨平台项目 |
| `false` | 完全不管，一切按 `.gitattributes` 来 | **有 `.gitattributes` 时的推荐值** |

> 注意优先级：**`.gitattributes` 里写死的 `eol=` 会覆盖 `core.autocrlf`。** 所以只要项目里有 `* text=auto eol=lf`，你在 `autocrlf` 上怎么配都不太会影响结果——这就是"把规则写进仓库"比"靠每个人本地配置"更可靠的原因。

### 那两个警告是什么意思

```text
warning: in the working copy of 'calc.py', LF will be replaced by CRLF the next time Git touches it
```

翻译：**你工作区里这个文件是 LF，但按当前配置，下次检出会变成 CRLF。**

```text
warning: in the working copy of 'calc.py', CRLF will be replaced by LF the next time Git touches it
```

反过来：**你文件里是 CRLF，提交时会存成 LF。**

两个都**不影响提交的内容正确性**，只是提醒"工作区的换行符和仓库设定不一致"。判断要不要管：

- 只有一两行警告、`git diff` 里没有异常的大段改动 → 可以忽略
- 每个文件都警告、或者 `git status` 显示 modified 但 `git diff` 是空的 → 说明配置和 `.gitattributes` 打架了，统一成 `core.autocrlf false` + `* text=auto eol=lf`

> 顺带说一句：`git status` 显示 modified、`git diff` 却空白，这是换行符问题的典型症状（git 比较时会做规范化，所以看不到差异）。`git add --renormalize .` 能一次性修好。

### 已有一堆 CRLF 的文件怎么办

```powershell
git add --renormalize .        # 按新规则重新规范化所有文件
git commit -m "chore: 统一换行符"
```

## 6. Git Hooks：提交前自动检查

`.git/hooks/` 里的脚本，在特定时机自动跑。最常用 `pre-commit`（提交前）：

```powershell
# .git/hooks/pre-commit  （Linux/Mac 版本，Windows 上可用 Git Bash）
#!/bin/sh
python -m unittest discover -s tests -q || {
  echo "测试没过，不许提交"
  exit 1
}
```

Windows 上（PowerShell 脚本）：

```powershell
# .git/hooks/pre-commit 内容指向 ps1
# 实际做法：用 husky / pre-commit 这类工具，跨平台且能提交到仓库里共享
```

**问题：`.git/hooks/` 不进版本控制**，每个人的钩子都得自己配。所以工程上一般用：

- **Python**：`pre-commit`（`pip install pre-commit`，配置写 `.pre-commit-config.yaml`，进仓库）
- **JS**：`husky` + `lint-staged`
- 或者干脆交给 CI——本地钩子可以绕过（`git commit --no-verify`），CI 不能

**建议：本地钩子求快（格式化、lint），硬性质量门禁放 CI。**

## 7. 大文件

Git 不适合存二进制大文件（每改一次存一份完整副本，仓库会爆炸）。

```powershell
# 装 Git LFS
git lfs install
git lfs track "*.psd"
git add .gitattributes
```

或者干脆别放（设计稿、数据集放对象存储）。**已经开始用了才发现仓库 2GB？** 需要 `git filter-repo` 重写历史，很痛，提前规划。

## 8. Code Review 里和 Git 相关的几件事

**看别人的 PR 前，先在本地跑起来：**

```powershell
git fetch origin
git switch -c review/xxx origin/feature/xxx
python -m unittest discover -s tests -v
git switch main
git branch -D review/xxx
```

**只看这个 PR 带来的改动**（不含主干上的别人的改动）：

```powershell
git diff main...origin/feature/xxx
```

**review 意见的标准回复方式：**

```powershell
# 改代码
git add -A
git commit -m "fix: 按 review 意见处理空关键词"
git push
```

**加新提交，不要 amend 已推送的提交**——否则 review 页面上的历史对不上，评论会错位。合并时平台会用 squash 帮你压成一条。

## 9. 团队禁忌清单

| ❌ 别做 | 为什么 | 该怎么做 |
| --- | --- | --- |
| 在 main 上直接开发 | 别人没法基于稳定版本工作 | 开分支 |
| `git push --force` 公共分支 | 抹掉别人的提交 | `--force-with-lease`，且只对私有分支 |
| 提交 `data/`、`__pycache__`、`.env` | 污染仓库、泄露密钥 | `.gitignore` |
| 把密钥写进代码再删掉 | 历史里还在，`git log -p` 能翻出来 | 用环境变量，密钥泄露要立刻轮换 |
| 一次提交改 40 个文件 | 没法 review、没法回滚 | 拆成多次 |
| 提交信息写 `update` | 历史不可读 | 写清类型和原因 |
| 一周不 pull | 冲突爆炸 | 每天 pull |
| `reset --hard` 前不 `status` | 未提交改动无声消失 | 先看，或先 stash |
| 在共享分支上 rebase | 所有人历史分叉 | 只在私有分支 rebase |
| 分支活一个月 | 合并时地狱 | 小步快跑 |

## 10. 一份可以直接抄的 `git config`

```powershell
git config --global user.name "你的名字"
git config --global user.email "you@example.com"
git config --global init.defaultBranch main
git config --global core.quotepath false
git config --global core.autocrlf false
git config --global pull.rebase false
git config --global push.default simple
git config --global fetch.prune true
git config --global core.editor notepad
git config --global alias.lg "log --oneline --graph --all --decorate"
git config --global alias.st "status -sb"
git config --global alias.last "log -1 HEAD --stat"
git config --global alias.unstage "restore --staged"
git config --global alias.undo "reset --soft HEAD~1"
```

最后两个别名很实用：`git unstage <file>` 取消暂存，`git undo` 撤销上一次提交但保留改动。
