# 01 · 概念模型：Git 到底在存什么

> 这一章不教命令，只建模型。模型建对了，后面所有命令都是"显然的"；模型错了，就只能死记硬背，遇到情况就慌。

---

## 1. Git 存的是快照，不是差异

大多数版本控制工具存的是"每一版改了什么"。Git 不是——**每提交一次，Git 就把当时所有文件拍一张完整的快照**，然后存起来。

一张快照（一个 commit）长这样：

```
commit  ← 一次提交：谁、什么时候、为什么（提交信息）、上一张快照是谁
  └── tree（目录树）
        ├── blob  ← README.md 的内容
        ├── tree  ← todo/ 目录
        │     ├── blob  ← cli.py 的内容
        │     └── blob  ← store.py 的内容
        └── blob  ← .gitignore 的内容
```

几个要点：

- **内容相同只存一份。** 一个文件没改，新快照里直接指向同一个 blob。所以"存全量快照"并不浪费空间。
- **blob 的名字是内容的哈希。** 内容变一个字，哈希就变。所以 Git 能靠比对哈希瞬间判断"这两个文件一样吗"。
- **commit 的哈希由内容算出。** 父提交、树、作者、时间、信息任何一项变了，哈希就变了——这正是 `git commit --amend` 会"换一个新提交"的原因。
- 你在终端里看到的那串 `a51ac64`，是完整 40 位哈希的前 7 位，够用了。

**为什么要懂这个？** 因为后面所有的"改写历史"（amend / rebase / reset）本质都一样：**造一批新快照，然后把分支指针挪过去**。旧快照并没有被删除，它们还在磁盘上（默认 30 天后才被回收），所以 `reflog` 能救命。

## 2. 四个区域（三棵树 + 一个远程）

Git 的日常操作，全部可以归结为"把改动从一个区域搬到另一个区域"。

```
   工作区                暂存区                本地仓库              远程仓库
 Working Tree   →      Index/Stage    →      Repository     →      Remote
 （你正在编辑的      （git add 之后      （git commit 之后      （git push 之后
   文件）              待提交的清单）       的提交历史）           的服务器副本）

        ←──── git checkout/restore ────┘
                       ←──── git reset ─────┘
                                          ←──── git fetch/pull ────┘
```

| 区域 | 物理位置 | 存放什么 | 谁往里放 |
| --- | --- | --- | --- |
| 工作区 | 你能用编辑器打开的文件 | 当前内容（可能改了一半） | 你，用编辑器 |
| 暂存区 | `.git/index` 一个文件 | 下次提交要包含的"文件+内容"清单 | `git add` |
| 本地仓库 | `.git/objects` | 所有 commit / tree / blob | `git commit` |
| 远程仓库 | 服务器（或另一个目录） | 同样的对象，另一份 | `git push` |

### 暂存区为什么存在？

因为它让"一次提交"可以**从改动里挑**。

举个真实场景：你为了改 A 功能，顺手修了 B 文件里一个拼写错误、又删了几行调试代码。没有暂存区，你只能一次全提交，或者手工把改动抄出来。有了暂存区：

```powershell
git add todo/search.py        # 只把 A 功能加入这次提交
git commit -m "feat: 支持搜索"
git add -u                    # 剩下的（改的、删的）加入下一次提交
git commit -m "chore: 清理调试代码"
```

一次提交 = 一件事，历史才可读、可回滚。暂存区就是干这个用的。

## 3. 文件只有四种状态

```
        git add                    git commit
未跟踪 ─────────→ 已暂存 ─────────→ 已提交（未修改）
Untracked         Staged            Unmodified
                    ↑                    │
                    │     编辑文件        │
                    └──── 已修改 ←────────┘
                          Modified
```

- **未跟踪 Untracked**：Git 从没见过这个文件。`git status` 里显示 `??`。不 `add` 就永远不会被提交。
- **已修改 Modified**：文件被跟踪了，但内容和上次提交不一样。显示 ` M`。
- **已暂存 Staged**：改动已被 `add` 进暂存区，下次 `commit` 会包含它。显示 `M `（注意 M 在左边）。
- **已提交 Unmodified**：工作区、暂存区、最新提交三者一致，`git status` 什么都不显示。

> `git status --short`（别名 `git st`）里，**左边一列是暂存区，右边一列是工作区**。`MM` 表示：暂存了一份改动，之后又改了但没 add。这个两列布局能省很多困惑。

## 4. 分支和 HEAD 都是"指针"

```
                  main
                   ↓
  A ← B ← C ← D ← E
                   ↑
                  HEAD（你在这）
```

- **分支 = 一个指向某个提交的可移动指针。** 不是文件夹副本，不是"另存为"。创建一个分支就是写一个 40 字节的文件。所以建分支是零成本的，随便建。
- **HEAD = 指向"当前分支"的指针。** 你 `git switch feature`，HEAD 就指向 `feature`；之后你提交，`feature` 往前走，HEAD 跟着它。
- HEAD 也可以直接指向某个提交，这叫**分离头指针（detached HEAD）**——此时提交不属于任何分支，切走就可能"丢"（但能用 reflog 找回来，见 docs/06）。

一句话记住：**提交让当前分支前进一格；切换分支让 HEAD 换指向，同时把工作区文件换成那个分支的快照。** 这就是"切分支时文件会变"的全部原因。

## 5. 命令与区域的对应关系

记住这张表，就不用背命令了——想清楚"我要把改动从哪搬到哪"，命令自然出来。

| 我想…… | 命令 | 动的是 |
| --- | --- | --- |
| 看现在什么状态 | `git status` | 只读 |
| 看工作区 vs 暂存区 | `git diff` | 只读 |
| 看暂存区 vs 最新提交 | `git diff --staged` | 只读 |
| 看最新提交改了什么 | `git show` | 只读 |
| 工作区 → 暂存区 | `git add <file>` | 暂存区 |
| 暂存区 → 本地仓库 | `git commit` | 本地仓库 + 分支指针 |
| 暂存区 → 工作区（取消 add） | `git restore --staged <file>` | 暂存区 |
| 丢弃工作区改动（回到上次提交） | `git restore <file>` | 工作区 |
| 本地仓库 → 暂存区 + 工作区（撤销提交） | `git reset --hard <commit>` | 三个都动，危险 |
| 本地仓库 → 远程 | `git push` | 远程 |
| 远程 → 本地仓库 | `git fetch` | 本地仓库（`origin/xxx`） |
| 远程 → 本地仓库 + 工作区 | `git pull` | 全都动 |

> `git restore` / `git switch` 是 Git 2.23 才拆出来的新命令。你以前可能见过 `git checkout -- <file>` 和 `git checkout -b <branch>`——功能一样，只是 `checkout` 一个命令管两件不相干的事，太容易搞混，所以官方拆开了。新代码一律用新的。

## 6. 五个常见误解

**误解 1：`git add` 是"保存"。**
不是。`add` 只是把内容放进暂存清单，文件内容一点没变，历史也一点没变。真正的"保存"是 `commit`。

**误解 2：删了分支，提交就没了。**
删分支只是删掉一个指针。只要那些提交还被别的分支或 tag 指着，或者还在 reflog 里，就能找回来。真正删除要等 `git gc` 清理不可达对象（默认 30 天）。

**误解 3：`git commit` 会把工作区所有改动都存进去。**
只存**暂存区里的**。工作区里没 `add` 的改动不会进这次提交。这是新手最常踩的坑（"我明明改了，怎么提交里没有"）。

**误解 4：切分支会把当前改动带走。**
如果工作区有未提交的改动，Git 会尽量把它们"带过去"（因为文件内容不改），但如果目标分支上同一个文件内容不同，Git 会拒绝切换并报错 `Your local changes would be overwritten`。此时该 `commit` 或 `stash`，不是硬切。

**误解 5：远程仓库是"备份"。**
远程是**协作的集散地**，不是备份盘。备份应该另有方案。远程的价值在于：所有人有个共同的参照点，`origin/main` 就是"大家公认的主干长什么样"。

## 7. 这一章要带走的三句话

1. **提交是快照，分支是指针，HEAD 指向当前分支。**
2. **所有操作都是在四个区域之间搬东西。**
3. **先 `git status`，再动手。**
