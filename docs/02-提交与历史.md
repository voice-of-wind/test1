# 02 · 提交与历史：日常最常用的 10 条命令

> 这一章的命令你每天都会用。目标不是记住所有参数，而是**看得懂输出**——因为 Git 的所有问题，答案基本都在 `status` / `diff` / `log` 的输出里。

---

## 1. `git status`：读懂它，一半问题就没了

```powershell
git status
```

三种典型输出的第一行，就是答案：

```text
On branch main                                   ← 我在 main 上
Your branch is up to date with 'origin/main'.    ← 和远程一致

Changes not staged for commit:                   ← 改了但没 add
  (use "git add <file>..." to update what will be committed)
  (use "git restore <file>..." to discard changes in working directory)
        modified:   README.md

Untracked files:                                 ← Git 从没见过
  (use "git add <file>..." to include in what will be committed)
        data/

no changes added to commit (use "git add" and/or "git commit -a")
```

`git status` 的括号里经常直接写着**下一步该敲什么命令**。新手最爱问的"现在怎么办"，它已经回答了。

日常用短格式更方便：

```powershell
git status --short      # 或别名 git st
```

```text
 M README.md       ← 右边 M：工作区改了，没 add
M  README.md       ← 左边 M：已 add，等提交
MM README.md       ← 两边都有：add 了一份，之后又改了
?? data/           ← 未跟踪
A  todo/new.py     ← 新增且已 add
D  old.txt         ← 删除且已 add
```

**两列的含义固定：左=暂存区，右=工作区。**

### 特殊情况

```text
You are in the middle of a merge.        ← 合并没做完（有冲突没解）
HEAD detached at a51ac64                 ← 分离头指针，此刻的提交不属于任何分支
Your branch is ahead of 'origin/main' by 2 commits.   ← 本地比远程多 2 个提交，该 push
Your branch is behind 'origin/main' by 1 commit.      ← 远程比你新，该 pull
```

看到 `detached HEAD` 先别提交，先想清楚"我为什么不在分支上"（见 docs/03）。

## 2. `git add`：把改动放进暂存区

```powershell
git add README.md              # 指定文件
git add docs/                  # 整个目录
git add .                      # 当前目录下所有改动（含新增）
git add -A                     # 整个仓库所有改动（含删除）——最常用
git add -u                     # 只处理已被跟踪的文件（改的、删的），不含新增
git add "*.py"                 # 按通配符（PowerShell 里要加引号，否则自己先展开了）
```

### `git add -p`：把一个大改动拆成几次提交

这是把提交做小的关键技能。它会一段一段（hunk）问你：

```powershell
git add -p todo/store.py
```

```text
@@ -40,6 +40,7 @@ class TaskStore:
     def add(self, title, priority="normal"):
+        """新增一条任务。"""
         task = Task(id=self._next_id, title=title)
Stage this hunk [y,n,q,a,d,s,e,?]?
```

| 按键 | 意思 |
| --- | --- |
| `y` | 这段要 |
| `n` | 这段不要 |
| `s` | 这段太大，再拆小一点 |
| `e` | 手工编辑这段（高级） |
| `q` | 退出，已选好的生效 |

配合 `git diff` 先看全貌，再用 `-p` 挑，你就能做到"改了一堆，但提交了三条干净的历史"。

## 3. `git commit`：真正落盘

```powershell
git commit -m "feat(cli): 支持用 -t 打标签"          # 单行
git commit                                            # 不带 -m：打开编辑器写多行
git commit -am "fix: 修掉空文件崩溃"                   # add 已跟踪文件 + commit 一步完成
git commit --amend -m "feat(cli): 支持多个标签"        # 改最后一次提交（内容或信息）
git commit --amend --no-edit                          # 内容改了，信息不变
```

### 关于 `-am` 的坑

`-am` 只对**已被跟踪**的文件生效。新建的文件（untracked）它不会管，所以经常出现"我 `-am` 了，怎么新文件没进去"。**变量少的时候，老老实实 `git add -A` 再 `commit` 更可靠。**

### `--amend` 的真相

它不是"修改"，而是**丢掉上一次提交，造一个新的**——哈希会变：

```text
b57aef3 docs: 补充贡献说名      ← amend 前
e727277 docs: 补充贡献说明      ← amend 后（哈希变了，旧提交还在 reflog 里）
```

所以：**已经 push 出去的提交不要 amend**，否则你本地和远程的历史就不一样了，别人一 pull 就出事（见 docs/06）。

### 提交信息怎么写

```text
<类型>(<范围>): <一句话>

<可选正文：为什么这么改，而不是改了什么>
```

```text
feat(store): 增加任务统计

原来的 list 只能看条数，想知道"这周完成了多少"得自己数。
现在加一个 stats()，CLI 里对应 stats 子命令。
```

好信息回答"**为什么**"，因为"改了什么"看 diff 就知道。反例：`update`、`修改`、`fix bug`、`111`、`test`——半年后你自己都想骂人。

## 4. `git diff`：看清"到底改了什么"

四个最常用的形态，**注意对比的两端是谁**：

```powershell
git diff                     # 工作区 ↔ 暂存区（还没 add 的改动）
git diff --staged            # 暂存区 ↔ 最新提交（这次 commit 会提交什么）
git diff HEAD                # 工作区 ↔ 最新提交（所有未提交的改动，不管 add 没 add）
git diff main feature/search # 两个分支的差别
git diff HEAD~2 HEAD         # 两个提交的差别
```

加参数看不同视角：

```powershell
git diff --stat              # 只列文件 + 增删行数
git diff --name-only         # 只列文件名
git diff --word-diff         # 按词比，适合看长段落文档改了哪几个字
git diff -U0                 # 只显示改动的行，不带上下文
git diff -- todo/store.py    # 只看某个文件
```

### 怎么读一段 diff

```diff
diff --git a/README.md b/README.md          ← 比的是哪两个文件
index c25170b..f0d1440 100644               ← 旧 blob..新 blob + 文件模式
--- a/README.md                             ← 旧版本
+++ b/README.md                             ← 新版本
@@ -97,3 +97,7 @@ project/                   ← 旧文件从第 97 行起 3 行；新文件从第 97 行起 7 行
 - 数据导出成 Markdown                       ← 前面是空格：上下文，没变
                                             ← 空行也是上下文
 > 注意：这个仓库**一开始没有 `.git`**...     ← 上下文
+                                            ← + 号：新增
+## 贡献                                     ← + 号：新增
+                                            ← + 号：新增
+改完代码先跑测试，再提 PR。                  ← + 号：新增
```

- `+` 绿 = 新增，`-` 红 = 删除，空格 = 未变的上下文。
- `@@ ... @@` 是"hunk 头"，告诉你这段在文件的哪个位置。**冲突时的 `<<<<<<<` 也是出现在这个层级**，理解它有助于看懂冲突（见 docs/04）。
- 如果一个文件你只改了一个空格，diff 里就是 `-` 一行 `+` 一行——这就是为什么"别顺手格式化整个文件"，会把真正的改动埋掉。

## 5. `git log`：看历史

```powershell
git log --oneline --graph --all --decorate    # ★ 最常用，别名 git lg
git log -5                                     # 最近 5 条
git log --stat                                 # 每条提交改了哪些文件
git log -p                                     # 每条提交的完整 diff（多，慎用）
git log -- todo/store.py                       # 只看某个文件的历史
git log --author="mshx"                        # 按人筛
git log --since="2 weeks ago" --until="yesterday"
git log -S "def search"                        # ★ 搜"哪次提交增删了这段代码"
git log --follow todo/old_name.py              # 跟着重命名走
git log main..feature/search                   # feature 有、main 没有的提交
git log feature/search..main                   # main 有、feature 没有的提交
```

`--oneline --graph --decorate` 三个参数合起来长这样：

```text
*   2b27f7b (HEAD -> main) merge: 合并搜索功能
|\
| * 042f020 (feature/search) feat(store): 支持按关键词搜索任务
|/
* 22230a1 chore: 初始化 todo 项目
```

- `*` 是提交，`|` `/` `\` 是分叉和汇合，左边的竖线是分支走向。
- 括号里是**引用**：哪个分支、哪个 tag、HEAD 在哪。`--decorate` 就是干这个的。
- 两个空格缩进的 `| *` 表示"这条在主线的旁边"。

> **`-S` 是排查 bug 的利器**：`git log -S "// 临时跳过校验"` 能直接找出是谁、哪次提交加了这段可疑代码。

## 6. `git show` / `git blame`：看单点细节

```powershell
git show HEAD                      # 最近一次提交的完整信息和 diff
git show HEAD --stat               # 只看改了哪些文件
git show HEAD:todo/store.py        # 看某个提交时这个文件的内容（不改工作区）★
git show v1.0.0                    # 看某个 tag
git blame todo/store.py            # 每一行是谁、哪次提交写的
git blame -L 40,60 todo/store.py   # 只看 40-60 行
```

`git show HEAD:文件路径` 特别有用：想知道"上一个版本这个函数长什么样"，不用切分支，直接看。反过来 `git show HEAD~1:README.md > old.md` 可以把旧版本导出。

`git blame` 的用途不是追责，是**找上下文**：这个奇怪的分支判断是谁为什么加的？拿到哈希，`git show <哈希>` 看当时的提交信息，通常就明白了。

## 7. 一次干净的提交长什么样

```powershell
git status                 # 1. 确认在正确的分支、只有想提交的文件
git diff                   # 2. 确认改的内容是我想改的
git add -p                 # 3. 挑出这次要提交的部分
git diff --staged          # 4. 再看一遍将要提交的内容
git commit -m "feat: ..."  # 5. 写清楚为什么
git log --oneline -3       # 6. 确认历史符合预期
```

第 4 步很多人跳过，但它能拦住 90% 的"提交里混进了不该有的东西"。
