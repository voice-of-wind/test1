# 03 · 分支：一个 40 字节的文件

---

## 1. 分支到底是什么

```text
        main
         ↓
  A ← B ← C ← D
```

`main` 就是 `.git/refs/heads/main` 这个文件，内容是一行哈希。就这么简单。

所以：

- **创建分支**：写一个文件，内容是当前提交的哈希。**几毫秒，零成本。**
- **切换分支**：改 `HEAD` 的内容，然后把工作区文件换成目标分支的快照。**成本取决于文件多少。**
- **提交**：当前分支那个文件里的哈希，换成新提交的哈希。

对比一下：在 SVN 里建分支 = 在服务器上复制一份目录。这就是为什么"Git 分支随便建"在 SVN 时代是不可想象的。

> 记住这句话：**分支不是文件夹的副本，是一个指向提交的标签。** 你删掉分支，提交还在（只要还有别的东西指着它）。

## 2. HEAD：你在哪儿

```text
        main
         ↓
  A ← B ← C
         ↑
        HEAD
```

`HEAD` 通常是一个**指向分支的指针**（`.git/HEAD` 里写着 `ref: refs/heads/main`）。它回答"我现在在哪条分支上"。

### 分离头指针（detached HEAD）

如果你直接 checkout 一个提交哈希或 tag：

```powershell
git checkout a51ac64
```

`HEAD` 就直接指向那个提交，不再指向任何分支：

```text
Note: switching to 'a51ac64'.
You are in 'detached HEAD' state. ...
```

**此时提交会怎样？** 提交本身是有效的，但**没有任何分支指着它**。你一旦 `git switch main`，就"看不见"它了——只是看不见，没丢，能用 `git reflog` 找回来（docs/06）。

什么时候会进 detached HEAD？

- 想看某个历史版本：`git checkout <哈希>`（看完 `git switch -` 回来）
- `git checkout v1.0.0` 看 tag
- `git bisect` 过程中（正常，Git 自己在切）
- `git rebase` 过程中（正常）

**规则：如果你在 detached HEAD 上写了东西还想留，先建个分支：**

```powershell
git switch -c rescue/my-work
```

## 3. 常用命令

```powershell
git branch                          # 列出本地分支（当前分支带 *）
git branch -vv                      # ★ 带每个分支的最新提交 + 跟踪的远程分支
git branch -a                       # 含远程分支（remotes/origin/xxx）
git branch -r                       # 只看远程分支
git branch feature/search           # 在当前提交上建分支（不切过去）
git switch feature/search           # 切过去
git switch -c feature/search        # 建 + 切，最常用
git switch -                        # 切回上一个分支（像 cd -）
git branch -m old-name new-name     # 改名（-m = move）
git branch -d feature/search        # 删除（已合并才让删）
git branch -D feature/search        # 强制删除（没合并也删，慎用）
git push origin --delete feature/search   # 删远程分支
```

### `git branch -vv` 的输出怎么读

```text
* main                2b27f7b [origin/main: ahead 2] merge: 合并搜索功能
  feature/search      042f020 feat(store): 支持按关键词搜索任务
```

- `*` 当前分支
- `[origin/main: ahead 2]` 跟踪 `origin/main`，本地领先 2 个提交（该 push 了）
- `behind 1` 落后 1 个（该 pull 了）
- `[origin/main: gone]` 远程那边已经删了这个分支，本地可以清掉
- 方括号里什么都没有 = 没有设置上游跟踪分支（第一次 push 时加 `-u` 就有了）

### `switch` 和 `checkout` 的关系

| 老命令（还能用） | 新命令（推荐） | 干什么 |
| --- | --- | --- |
| `git checkout -b x` | `git switch -c x` | 建分支并切过去 |
| `git checkout x` | `git switch x` | 切分支 |
| `git checkout -- file` | `git restore file` | 丢弃工作区改动 |
| `git checkout <哈希>` | `git switch --detach <哈希>` | 分离头指针 |

老命令 `checkout` 一个词干三件不相干的事（切分支 / 撤销文件 / 看历史），这是 Git 最容易让人懵的地方。2.23 之后拆开了，新代码别再用 `checkout`。

> 例外：`git checkout -- <file>` 在网络上的老教程里到处都是，看到时知道它等于 `git restore <file>` 即可。

### 删除分支时的那个报错

```powershell
git branch -d feature/search
# error: The branch 'feature/search' is not fully merged.
```

意思是：**这个分支上有提交还没合并到别处，删了你可能就找不到它们了。** Git 在保护你。

两种正确反应：

1. 还没合并完 → 别删，先合并（docs/04）
2. 确定不要了 → `git branch -D`（强删，但提交还在 reflog 里，30 天内能救）

## 4. 切分支时工作区会发生什么

这是新手最迷惑的一点。规则很简单：

**Git 会把工作区里被跟踪的文件，改成目标分支那次提交的样子。**

```powershell
git switch main
# todo/search.py 从"有 search 函数"变回"没有"
```

那**未提交的改动**呢？

- 如果目标分支上这些文件的内容和你当前分支一样 → 改动被"带过去"（文件没动，你继续写）
- 如果不一样 → Git 拒绝切换：

```text
error: Your local changes to the following files would be overwritten by checkout:
        todo/store.py
Please commit your changes or stash them before you switch branches.
```

**正确做法**（不是硬来）：

```powershell
git commit -am "wip: 半成品"     # 选项一：提交（哪怕信息写得糙）
git stash push -m "半成品"       # 选项二：先收起来，回头 git stash pop
```

`git switch -f`（强制）会**丢掉你的改动**，别用。

## 5. 分支怎么命名、怎么划分

命名要有信息量。团队里通用的前缀：

```text
feature/search          新功能
fix/empty-json-crash    修 bug
docs/git-guide          文档
chore/bump-python       杂活
refactor/store-split    重构
```

规则：**小写、连字符、带类型前缀**。避免 `test`、`dev1`、`我的分支`、`zhang/dev`（除非团队规定带人名）。

### 什么时候开分支

- 做一件事超过 30 分钟 → 开分支
- 需要试错（不确定方案行不行）→ 开分支，不要污染 main
- 要给别人 review → 开分支
- 只是改个错别字 → 直接在 main 上提交也行（团队允许的话）

**一条分支只做一件事。** 一条分支上混了三件事，合并时冲突会翻倍，review 也没法看。

### 主干叫什么

新仓库用 `main`。老仓库可能叫 `master`——只是名字，没有技术区别。改名：

```powershell
git branch -m master main
git push -u origin main
# 然后在平台上把默认分支改成 main，再删掉远程的 master
```

## 6. 小练习（不用等 lab）

在 `project/` 里（做完 lab01 之后）：

```powershell
git switch -c experiment/hello
# 随便改一行 README
git commit -am "docs: 试一下分支"
git switch main
# 打开 README 看——改动没了，因为它在 experiment/hello 上
git switch experiment/hello
# 又回来了
```

这个"文件跟着分支变"的体验，做一次就理解了。
