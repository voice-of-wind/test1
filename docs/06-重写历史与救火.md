# 06 · 重写历史与救火

> 前面几章是"正常上班"，这一章是"改历史"和"出事了怎么办"。
> 核心认知：**Git 几乎不删东西。** 被"改写"掉的提交还在磁盘上，`reflog` 记着你每一次移动。

---

## 0. 先立规矩

会改写历史（换掉 commit 哈希）的操作：

```text
git commit --amend         改最后一次提交
git rebase                 把提交重放到新基底
git rebase -i              改造提交本身（合并/改写/删除/重排）
git reset                  把分支指针往回挪
git cherry-pick            复制提交（旧的还在，新的另一份）
git filter-repo            批量改写（很少用）
```

**铁律：已经 push 到公共分支的历史，不要改写。**

因为别人的本地仓库里有旧提交，你一改写，两边的历史就分叉了，别人一 pull 就人间惨剧。所以：

- 只在你**独占**的分支上改写
- 主干（main / master / develop）永远只做"追加"，不做改写
- 改写过的分支推上去，用 `--force-with-lease`，且提前在群里说一声

## 1. `git commit --amend`：改最后一次提交

```powershell
git commit --amend -m "feat(cli): 支持多个标签"   # 只改信息
git add forgotten_file.py
git commit --amend --no-edit                       # 补上漏掉的文件，信息不变
```

本质：**丢掉旧提交，用当前暂存区造一个新的**。哈希必变。

```text
b57aef3 docs: 补充贡献说名      ← 原来
e727277 docs: 补充贡献说明      ← amend 后
```

旧的那个 `b57aef3` 还在，`git reflog` 里能看到。

**只能改最后一次。** 想改更早的，用 `rebase -i`。

---

## 2. `git rebase`：换基底

### 它在做什么

```text
rebase 前：
        D ← E            ← main
       /
  A ← B ← F ← G          ← feature（HEAD）

git switch feature
git rebase main

rebase 后：
        D ← E            ← main
       /     \
  A ← B       F' ← G'    ← feature（HEAD）
```

Git 把 `F`、`G` 这两个提交的**改动**，一个个"重放"到 `E` 上，造出 `F'` 和 `G'`。

注意：**`F'` 和 `G'` 是新的提交，哈希变了**。旧的 `F`、`G` 被丢弃（但还在 reflog 里）。

### 和 merge 的区别

| | merge | rebase |
| --- | --- | --- |
| 历史形状 | 有分叉、有合并提交 | 一条直线 |
| 提交哈希 | 不变 | 全变 |
| 是否安全 | 安全（不改历史） | 只适合私有分支 |
| 冲突 | 解决一次 | **可能每个提交都要解一次** |

**选择原则：**

- 主干合并功能分支 → 用 `merge`（保留"这里合并过"的事实）
- 本地分支跟上主干 → 用 `rebase`（让历史保持直线，避免"合来合去"的蜘蛛网）

### 操作

```powershell
git switch feature/search
git fetch origin
git rebase origin/main

# 如果有冲突：
#   1. 解决冲突（注意！rebase 时 ours/theirs 是反的）
#   2. git add <files>
#   3. git rebase --continue
#   4. 想放弃：git rebase --abort
#   5. 想跳过这个提交：git rebase --skip
```

### ⚠️ rebase 时 `--ours` / `--theirs` 是反的

这是 Git 最坑的命名，没有之一：

| 场景 | `--ours` | `--theirs` |
| --- | --- | --- |
| `git merge` | 你当前所在的分支 | 被合进来的分支 |
| `git rebase` | **你 rebase 到的那条基线（别人的）** | **你自己正在重放的提交** |

原因：rebase 的实现是"先切到基线，再把你的提交一个个打上去"，所以从 Git 的角度，"ours"是基线。

**建议：完全不用这两个参数，手工改。** 记不住就会丢代码。

## 3. `git rebase -i`：改造提交

这是"整理历史"的瑞士军刀。

```powershell
git rebase -i HEAD~4        # 改最近 4 个提交
git rebase -i <哈希>        # 改这个哈希之后的所有提交（不含它）
```

会打开编辑器（README 里配了 notepad），列出：

```text
pick 0d4bbe5 fix
pick 5256f6f 加乘法
pick 7fece51 加除法
pick 2f50b61 加类型注解

# Rebase 26cec45..2f50b61 onto 26cec45 (4 commands)
#
# Commands:
# p, pick   = 保留这个提交
# r, reword = 保留，但改提交信息
# e, edit   = 保留，但停下来让你改内容（可用来拆分提交）
# s, squash = 并入上一个提交，保留两者的信息
# f, fixup  = 并入上一个提交，丢弃这个的信息
# d, drop   = 删掉这个提交
```

把 `pick` 改成你要的动作，保存退出，Git 就按新剧本重放。

### 三个最常用的玩法

**① 把三条碎提交压成一条（squash）**

```text
pick   0d4bbe5 fix
squash 5256f6f 加乘法
squash 7fece51 加除法
```

保存后 Git 会让你编辑合并后的提交信息。写一条能说清整件事的即可。

**② 改历史里的提交信息（reword）**

```text
reword 5256f6f 加乘法      ← 把 "加乘法" 改成 "feat(calc): 支持乘法"
```

**③ 删掉一条不该有的提交（drop）**

```text
drop 7fece51 加除法      ← 那行调试代码就是这里加的，整个提交不要了
```

> **注意顺序**：`rebase -i` 列表里**从上到下 = 从旧到新**，和 `git log` 的显示顺序**相反**。这个反直觉的点坑过很多人。

### 编辑器不会用？

- `notepad`：直接改，存盘，关窗口 → Git 继续
- **如果卡在 vim 里**（看到 `~` 结尾的行，底部没有提示）：按 `i` 进入插入模式 → 改 → 按 `Esc` → 输入 `:wq` → 回车
- 想彻底不碰 vim：`git config --global core.editor notepad`

### 中途想放弃

```powershell
git rebase --abort        # 回到 rebase 前
```

任何时候都能退，不丢东西。

## 4. `git reset`：把指针挪回去

`reset` 有三个模式，区别只在**动哪几个区域**：

```text
                  --soft      --mixed(默认)    --hard
  分支指针(HEAD)    动            动             动
  暂存区            不动          动             动
  工作区            不动          不动           动  ← 丢代码！
```

### `--soft`：撤销提交，改动全留着（在暂存区）

```powershell
git reset --soft HEAD~1
```

用在你"提交早了/提交信息想重写/想重新组织提交"的时候。改动一点没丢，全在暂存区，直接再 `commit` 就行。

### `--mixed`（默认）：撤销提交 + 取消暂存，改动留在工作区

```powershell
git reset HEAD~1
```

改动还在文件里，只是需要重新 `git add`。

### `--hard`：连工作区一起回到那个提交

```powershell
git reset --hard HEAD~1
```

**未提交的改动直接消失，没有任何提示。** 这是 Git 里最危险的一条命令。

用之前问自己：**我真的不要这些改动了吗？** 不确定就先：

```powershell
git stash push -m "先存一下，以防万一"
```

### 常用组合

```powershell
git reset --hard HEAD          # 丢弃所有未提交改动（等价于全部 restore）
git reset --hard origin/main   # 让本地和远程完全一致（本地提交全丢）
git reset --soft HEAD~1        # 撤销上一次提交，重新提交
git reset HEAD~1 -- todo/a.py  # 只把某个文件从上次提交里拿出来（不动别的）
```

## 5. `git revert`：公共分支上正确的"撤销"

`reset` 是"把历史抹掉"，`revert` 是"**造一个新提交，内容正好把旧提交抵消**"。

```powershell
git revert <哈希>              # 造一个反向提交
git revert HEAD                # 撤销最近一次
git revert --no-commit <哈希>  # 先不提交，看看效果
```

```text
revert 前：  A ← B ← C
revert B 后：A ← B ← C ← B'     ← B' 抵消了 B 的改动，历史完整保留
```

**规则：已经推到公共分支的提交，要撤销就用 `revert`，不要用 `reset`。** 因为别人已经有那些提交了，你抹掉历史只会让大家分叉。

`revert` 也可能冲突（如果后面的提交又改了同一处），处理方式和 merge 冲突一样。

## 6. `git reflog`：后悔药（**这一节最该记住**）

Git 记录了**你每一次让 HEAD 移动的操作**：commit、switch、reset、rebase、merge……

```powershell
git reflog
```

```text
2f50b61 HEAD@{0}: reset: moving to HEAD~2
7fece51 HEAD@{1}: checkout: moving from 0d4bbe5 to 7fece51
0d4bbe5 HEAD@{2}: commit: fix
5256f6f HEAD@{3}: commit: 加乘法
```

只要提交曾经被 HEAD 指过，它就出现在这里。默认保留 **90 天**（不可达对象 30 天）。

### 经典救援：误用 `reset --hard`

```powershell
git reset --hard HEAD~3        # 手一抖，3 个提交没了
git reflog                     # 找到丢掉之前的那个位置
git reset --hard 'HEAD@{1}'    # 回去
```

### ⚠️ Windows / PowerShell 的坑

**`HEAD@{1}` 必须加引号！**

PowerShell 会把 `@{...}` 当成哈希表语法，直接报错：

```text
git: 'unknown switch `e'' 
```

```powershell
git reset --hard HEAD@{1}       # ❌ PowerShell 报错
git reset --hard 'HEAD@{1}'     # ✅ 单引号
git reset --hard "HEAD@{1}"     # ✅ 双引号也行
```

用 Git Bash 或 cmd 时不用加引号，但养成加引号的习惯没坏处。

### 其它用法

```powershell
git reflog show main          # 只看 main 分支的移动历史
git reflog --date=iso         # 带时间
git log -g --oneline          # 用 log 的格式看 reflog
git switch -c rescue 'HEAD@{3}'   # 从历史某个点开一条新分支（比 reset 更安全）
```

**注意**：reflog 是**本地的、私有的**，不会 push 到远程。所以它只能救你自己机器上的操作。

## 7. `git cherry-pick`：只搬一个提交

```powershell
git switch main
git cherry-pick 5d4bea2          # 把那个提交的改动搬过来，造一个新提交
git cherry-pick A..B             # 搬一个范围
git cherry-pick -n 5d4bea2       # 搬改动但不提交（-n = --no-commit）
git cherry-pick --abort          # 放弃
```

典型场景：

- 在 `feature` 上修了个 bug，主干也急着要 → 把那个修复提交 cherry-pick 到 main
- 合错了分支，想把某一条提交捞到别处

**代价**：cherry-pick 出来的提交哈希不同（是复制品）。同一个改动在两条分支上各有一份，将来合并时可能冲突。**能用 merge/rebase 解决就别用 cherry-pick。**

## 8. `git stash`：临时收起来

场景：改了一半，突然要切分支修个紧急 bug，又不想提交半成品。

```powershell
git stash push -m "搜索功能做了一半"      # 收起来（默认不含未跟踪文件）
git stash push -u -m "连新文件也收"        # -u 含未跟踪文件
git stash list                            # 看有哪些
git stash show -p stash@{0}                # 看内容（PowerShell 里注意引号）
git stash pop                             # 取出最近一个，并从栈里删掉
git stash apply stash@{1}                 # 取出指定的，但保留在栈里
git stash drop stash@{0}                  # 删掉一个
git stash clear                           # 清空（危险）
```

**注意**：`stash` 也是本地私有的，不会 push。它是"临时抽屉"，不是备份。

很多团队其实更推荐**直接开个 wip 提交**（`git commit -m "wip: 半成品"`），因为提交在 reflog 和分支里都看得见，比 stash 更不容易忘。stash 用久了会有一堆"这是什么"的条目。

## 9. `git bisect`：二分查找定位 bug

场景：30 个提交之前还是好的，现在坏了，不知道是哪次改坏的。

```powershell
git bisect start
git bisect bad                  # 当前版本是坏的
git bisect good v1.0.0          # 这个版本是好的（或某个哈希）

# Git 会切到中间那个提交，你测一下
git bisect good                 # 这个提交没问题
git bisect bad                  # 这个提交有问题
# ...重复 log2(N) 次，Git 就锁定第一个坏提交
git bisect reset                # 结束，回到原来的位置
```

9 个提交只要 3-4 次，1000 个提交也只要 10 次。

### 全自动

如果测试能自动判断好坏：

```powershell
git bisect start
git bisect bad
git bisect good HEAD~7
git bisect run python -m unittest -q
```

测试退出码 0 = good，非 0 = bad。Git 自己二分，最后告诉你：

```text
7fece51... is the first bad commit
    加除法
```

lab06 会真的这么跑一次。

## 10. `git worktree`：同一仓库多个工作目录

```powershell
git worktree add ../todo-hotfix fix/urgent     # 在另一个目录检出 fix/urgent
git worktree list
git worktree remove ../todo-hotfix
```

不用 stash 就能同时开两个分支干活（一个目录写新功能，一个目录修 bug），共享同一个 `.git`。分支多、任务切换频繁时很省事。

## 11. 出事了？按这个顺序想

```text
① 我只是想丢掉工作区的改动
   → git restore <file>

② 我提交了但想改信息 / 补文件（还没 push）
   → git commit --amend

③ 我想撤销最近一两次提交，但代码要留着
   → git reset --soft HEAD~n

④ 我 push 错了，想撤销（已经到公共分支）
   → git revert <哈希>，然后 push

⑤ 我 reset --hard 了，代码没了
   → git reflog，找到之前的位置，git reset --hard 'HEAD@{n}'

⑥ 我 rebase 乱了
   → git rebase --abort

⑦ 我 merge 乱了
   → git merge --abort

⑧ 我删了分支，提交还在里面
   → git reflog 找到哈希，git switch -c <新分支名> <哈希>

⑨ 完全不知道发生了什么
   → git status; git log --oneline --graph --all; git reflog | head -20
```

**最后一条最重要：不要慌，不要乱敲 `--force` 和 `--hard`。先看，再动。**
